Açılış: Sunum üç bölüm. Önce Java 8'i bu kadar stabil ve kalıcı yapan şeyi, sonra Java 9–17 yolculuğu, son olarak Java 21 ile ekibimiz için ne değişeceği. Kod kartları düzenlenebilir ve "Çalıştır" ile gerçek bir JDK 21 üzerinde (Compiler Explorer) çalışır; katılımcılardan kodu bozmalarını isteyin — derleyici hatalarını canlı görmek en öğretici kısım.

Tezim

Java 8 · JEP 122 — Remove the Permanent Generation

PermGen gitti, Metaspace geldi

Sınıf metaverisi artık heap'in içindeki sabit bir bölmede değil, yerel bellekte (native memory) tutuluyor.

PermGen neydi?

PermGen (Permanent Generation), HotSpot JVM'de heap'in içinde sabit boyutlu bir bölümdü. İçinde yüklenen sınıfların metaverisi, metot bilgileri, statik alanlar, sabit havuzu (constant pool) ve Java 6'ya kadar intern edilmiş String'ler dururdu. "Permanent" adı yanıltıcıydı: içeriği çöp toplamaya tabiydi, ama tavanı sabitti.

Sorun neydi?

  • Sabit tavan. -XX:MaxPermSize ile elle ayarlanırdı; varsayılan 64–85 MB civarındaydı. Doğru değeri önceden kestirmek neredeyse imkânsızdı.
  • Hot deploy sızıntısı. Uygulama sunucusuna her yeniden dağıtımda eski ClassLoader bellekte kalırsa sınıfları da kalırdı. Tomcat/JBoss'ta "üçüncü deploy'dan sonra sunucuyu yeniden başlat" alışkanlığı buradan gelir.
  • Çerçeveler şişiriyordu. Spring, Hibernate ve dinamik proxy üreten her kütüphane çalışma zamanında sınıf üretir; büyük uygulamalarda on binlerce sınıf PermGen'e sığmazdı.
  • Sonuç, herkesin ezbere bildiği hata: java.lang.OutOfMemoryError: PermGen space

Java 8 ne yaptı?

  • PermGen tamamen kaldırıldı; sınıf metaverisi Metaspace'e taşındı.
  • Metaspace heap'te değil, yerel bellekte yaşar ve varsayılan olarak otomatik büyür; pratik sınırı makinenin belleğidir. Artık "ne kadar ayıralım?" sorusu yok.
  • Bir ClassLoader çöp toplandığında ona ait tüm metaveri topluca boşaltılır.
  • -XX:PermSize ve -XX:MaxPermSize bayrakları kaldırıldı. Java 8+ bunları görürse uygulamayı yine de başlatır, sadece uyarır:
    OpenJDK 64-Bit Server VM warning: Ignoring option MaxPermSize; support was removed in 8.0

Java 8 · Default Methods

Arayüzler nasıl kırılmadan büyüdü?

Arayüze gövdeli metot eklenebilmesi, Java 8'in en görünmez ama en kritik değişikliğiydi.

Problem

Java 8'de Collection arayüzüne stream() eklenmesi gerekiyordu. Ama arayüze yeni bir metot eklerseniz, o arayüzü uygulayan dünyadaki tüm sınıflar derlenmez hale gelir. Milyonlarca satır kodu kırmadan Stream API'yi eklemenin yolu yoktu.

Çözüm: gövdeli arayüz metodu

Arayüz artık varsayılan bir gerçekleştirim taşıyabilir. Uygulayan sınıf isterse ezer, istemezse varsayılanı kullanır.

interface Liste<T> {
    void ekle(T t);

    default boolean bosMu() {   // yeni metot, kimse kırılmaz
        return boyut() == 0;
    }
}

Bu sayede gelen API'ler: Collection.stream(), Iterable.forEach(), Map.getOrDefault(), Map.computeIfAbsent(), Comparator.reversed(), Comparator.thenComparing(). Java 8'in Stream ve lambda dünyası bu mekanizma olmadan mümkün değildi.

Dikkat

  • Elmas problemi: iki arayüz aynı imzada default metot verirse sınıf derlenmez. Ezip Arayuz.super.metot() ile hangisini istediğinizi söylersiniz.
  • Durum yok: arayüzler alan tutamaz. Default metot, soyut sınıfın yerini almaz; API evrimi içindir.
  • Java 8 ayrıca arayüzlere static metot da getirdi: Comparator.comparing(...) bu sayede var.

Java 8 · CompletableFuture

Asenkron işleri zincirlemek

Java 5'in Future'ı yalnızca bloklayarak sonuç verirdi. CompletableFuture, "bittiğinde şunu yap" demeyi mümkün kıldı.

Eskiden

Future<Musteri> f = executor.submit(() -> musteriGetir(id));
Musteri m = f.get();          // thread burada BLOKLANIR
Siparis s = siparisGetir(m);  // ancak şimdi devam edebiliriz

Java 8 ile

CompletableFuture
    .supplyAsync(() -> musteriGetir(id))
    .thenApply(m -> siparisGetir(m))          // dönüştür
    .thenCombine(stokGetir(), (s, st) -> ...)  // iki işi birleştir
    .exceptionally(e -> varsayilanSiparis())   // hatayı yakala
    .thenAccept(System.out::println);          // sonucu kullan

allOf / anyOf ile birden çok işi bekleyebilir, orTimeout (Java 9) ile zaman aşımı koyabilirsiniz. Spring WebClient ve modern istemcilerin döndürdüğü tip budur.

Dikkat

  • Varsayılan havuz ortaktır. Executor vermezseniz ForkJoinPool.commonPool() kullanılır ve orada bloklayan iş yaparsanız tüm uygulamayı yavaşlatırsınız. Kendi executor'ınızı geçin.
  • Zincir uzadıkça yığın izi okunmaz hale gelir; hata ayıklama zorlaşır.
  • Java 21 notu: I/O bekleyen işler için sanal thread'lerle düz, bloklayan kod yazmak çoğu zaman daha okunur. CompletableFuture'ı işleri birleştirmek gerektiğinde tutun.

Java 8 · Paralel Stream & Fork/Join

Tek kelimeyle çok çekirdek

.parallelStream() işi böler, çekirdeklere dağıtır, sonucu birleştirir. Kolay olması onu her yerde doğru yapmaz.

Nasıl çalışır

Kaynak parçalara bölünür (spliterator), parçalar ForkJoinPool.commonPool() içindeki çekirdek sayısı - 1 kadar thread'e dağıtılır, sonuçlar birleştirilir.

double toplam = siparisler.parallelStream()
        .filter(s -> s.tutar() > 1000)
        .mapToDouble(Siparis::tutar)
        .sum();

Ne zaman kazandırır, ne zaman kaybettirir

UygunUygun değil
VeriOn binlerce eleman, ArrayList veya diziKüçük listeler, LinkedList, Stream.iterate
İşCPU yoğun, bağımsız hesapI/O bekleyen, veritabanına giden
Yan etkiYok, saf fonksiyonPaylaşılan listeye ekleme, sayaç artırma

Dikkat

  • Ortak havuz paylaşılır. Bir yerde bloklayan paralel stream, uygulamanın tamamındaki paralel işleri bekletir.
  • Ölçmeden kullanmayın: küçük verilerde bölme ve birleştirme maliyeti kazancı yer.
  • Java 21 notu: Sanal thread'ler I/O içindir, paralel stream CPU içindir. Birbirinin yerine geçmezler.

Java 8 · Nashorn (Java 15'te kaldırıldı)

JVM içinde JavaScript

Java 8, eski Rhino motorunun yerine Nashorn'u getirdi. Java 11'de kullanımdan kaldırıldı, Java 15'te silindi.

Ne işe yarıyordu

ScriptEngine motor = new ScriptEngineManager()
        .getEngineByName("nashorn");
motor.eval("var indirim = tutar > 1000 ? 0.1 : 0;");

Tipik kullanım: iş kurallarını yeniden derlemeden değiştirmek, kullanıcıya formül yazdırmak, şablon doldurmak. jjs komutuyla komut satırından da çalışırdı.

Neden gitti

ECMAScript 5.1'de kaldı, modern JavaScript'e (ES6 ve sonrası) hiç yetişemedi. Bakımı JDK için maliyetliydi. Java 11'de JEP 335 ile kullanımdan kaldırıldı, Java 15'te JEP 372 ile silindi.

Geçişte ne yapıldı

  • Bağımsız Nashorn: aynı motor artık ayrı bir kütüphane olarak var (org.openjdk.nashorn:nashorn-core). En hızlı çözüm, kodu değiştirmez.
  • GraalVM JavaScript: modern JS desteği isteyenler için.
  • Kural motoru: iş kuralları için betik yerine yapılandırma ya da kural kütüphanesi. Java 8 → 21 geçişinde en sık karşılaşılan somut kırılmalardan biri buydu.

Benim savunduğum prensip

KISS — Keep It Simple, Stupid

İki kod da aynı sonucu üretiyor: {Ankara={Elektronik=Ece (750.0)}, İzmir={Elektronik=Ayşe (2150.0), Kitap=Ayşe (300.0)}} — ikisini de çalıştırın.

KISS nedir?

1960'larda Lockheed'de Kelly Johnson'ın kuralı: bir sistem ne kadar basitse o kadar iyi çalışır. Yazılımdaki karşılığı, işi yapan en anlaşılır çözümü seçmektir.

Az satır ≠ basit

Soldaki tek bir ifade: ara sonucu göremezsiniz, ortasına kesme noktası koyamazsınız, hata izi hep aynı satırı gösterir. Sağdaki uzun ama her adımı ayrı test edilebilir.

Pratik ölçüt

Bir zincirde 3-4 adımı, bir lambda'da 1-2 satırı geçmeyin. İç içe collector yazmaya başladıysanız durun ve ara adımı isimlendirin.

Deneyin: soldaki koda kasten bir hata sokun (örneğin comparingByValue yerine comparingByKey) ve iki tarafta da hatayı bulmanın ne kadar sürdüğünü karşılaştırın.

Java 9 · Project Jigsaw (JPMS)

Modül sistemi nedir, ne işe yarar?

Güçlü kapsülleme

Yalnızca exports edilen paketler görünür. JDK'nın iç API'leri (sun.misc.Unsafe, com.sun.*) dışarıya kapandı.

Güvenilir yapılandırma

Eksik ya da çakışan bağımlılık, üretimde NoClassDefFoundError yerine uygulama açılırken hata verir.

Küçülebilen platform

JDK onlarca modüle bölündü. jlink ile yalnızca kullandığınız modüllerden çalışma zamanı üretirsiniz: ~300 MB yerine ~45 MB imaj.

Ama uygulamanız modül olmak zorunda değil: classpath (isimsiz modül) tam desteklidir ve çoğu ekip hâlâ böyle çalışıyor. Jigsaw'ın asıl etkisi, JDK'nın kendi kapılarını kapatması oldu; geçişte --add-opens ve --add-exports gerektiren şey budur.

Java 8 → Java 21
Jigsaw, Java 9'un en büyük ve en tartışmalı değişikliği. Üç cümlede özeti: modül = adı olan, neye ihtiyaç duyduğunu ve dışarıya ne verdiğini kendisi yazan bir paket kümesi. Ekiplerin çoğu kendi kodunu modüle çevirmedi, ama JDK modüler olduğu için herkes etkilendi: Hibernate, Spring, Mockito gibi kütüphaneler yansıma ile JDK'nın içine giriyordu ve o kapı kapandı. Sağdaki örneği çalıştırın; InaccessibleObjectException mesajı "module java.base does not opens java.lang" diyor, yani modül sistemi tam olarak burada devrede. Java 16'da (JEP 396) bu kapsülleme varsayılan, Java 17'de (JEP 403) kesin hale geldi; --illegal-access ile gevşetme yolu kalktı. Geçiş slaytındaki "--add-opens" maddesi bu slaytın devamıdır. Otomatik modüller (Automatic-Module-Name) kademeli geçiş için tasarlandı ama pratikte çoğu proje classpath'te kaldı.

Tek bir switch, üç kazanım

1

Tipi sor, değişkeni al

case KrediKarti k hem "bu bir kredi kartı mı?" diye sorar, hem de k değişkenini hazırlar. Ayrı bir cast satırı yok.

2

Alanları doğrudan aç

3

Odeme mühürlü olduğu için derleyici tüm tiplerin yazıldığını denetler. default yok: bir dalı silerseniz kod derlenmez.

Java 8'de aynı iş: if (o instanceof KrediKarti) { KrediKarti k = (KrediKarti) o; … } zinciri ve sonunda unutulmaya açık bir else.  ·  Gerekirse koşul da eklenir: case Havale h when h.tutar() > 10_000 -> …

Java 8 → Java 21
Bu slaytta tek bir kod var; üç maddeyi sırayla koddaki 1, 2, 3 yorumlarını göstererek anlatın. Canlı deneme: 2 numaralı satırı (Havale dalını) silip Çalıştır'a basın. Derleyici "the switch expression does not cover all possible input values" der; yani eksik senaryoyu testten önce derleyici yakalar. İsterseniz 1 numaralı dalı 'case KrediKarti(var no, var tutar) -> tutar * 0.02' diye değiştirip ayrıştırmanın iki dalda da çalıştığını gösterin. Java 8'den 21'e dil anlamındaki en büyük fark budur: visitor pattern'in çoğu kullanımı artık sadece bir switch.

Java 11 · JEP 321 — HTTP Client

Modern HTTP istemcisi JDK'nın içinde

Java 9'da deneme (incubator) olarak geldi, Java 11'de standart oldu. java.net.http paketi.

Eskiden

HttpURLConnection 1990'ların API'siydi: akış yönetimi elle, zaman aşımı ayarları dağınık, HTTP/2 yok, asenkron yok. Bu yüzden neredeyse her projede Apache HttpClient veya OkHttp bağımlılığı vardı.

Şimdi

HttpClient istemci = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .build();

HttpRequest istek = HttpRequest.newBuilder()
        .uri(URI.create("https://api.ornek.com/siparis/1042"))
        .header("Accept", "application/json")
        .timeout(Duration.ofSeconds(10))
        .GET()
        .build();

// Bloklayan
HttpResponse<String> y = istemci.send(istek, BodyHandlers.ofString());
System.out.println(y.statusCode() + " " + y.body());

// Asenkron: CompletableFuture döner
istemci.sendAsync(istek, BodyHandlers.ofString())
       .thenApply(HttpResponse::body)
       .thenAccept(System.out::println);

HTTP/2 varsayılan, WebSocket desteği var, gövde işleyicileri (BodyHandlers) akış, dosya ve byte dizisi için hazır geliyor.

Dikkat

  • HttpClient'ı yeniden kullanın. Bağlantı havuzunu o tutar; her istekte yenisini yaratmak havuzu anlamsız kılar.
  • Otomatik yeniden deneme, devre kesici (circuit breaker) ve ayrıntılı havuz ayarı yoktur. Bunlara ihtiyacınız varsa Apache HttpClient veya Resilience4j gibi bir katman gerekir.
  • Java 21 notu: sanal thread'lerle bloklayan send() çağrısı, asenkron sürüm kadar ölçeklenir ve okuması çok daha kolaydır.

Java 11 · JEP 330 — Tek dosya kaynak çalıştırma

Java 9 → 16 · Stream eklemeleri

Stream API on yılda olgunlaştı

Java 8'de gelen Stream, sonraki sürümlerde eksik kalan parçalarını tamamladı.

Java 9

// Sıralı veride koşul bozulana kadar al / bozulana kadar atla
loglar.stream().takeWhile(l -> !l.startsWith("ERROR")).toList();
loglar.stream().dropWhile(String::isBlank).toList();

// Koşullu iterate: for döngüsünün stream karşılığı
Stream.iterate(1, n -> n <= 100, n -> n * 2).forEach(...);

Stream.ofNullable(belkiNull);   // null ise boş stream

Java 12 ve 16

// teeing: aynı akışı iki toplayıcıya verip sonucu birleştir
var ozet = siparisler.stream().collect(
    Collectors.teeing(
        Collectors.counting(),
        Collectors.summingDouble(Siparis::tutar),
        (adet, toplam) -> adet + " sipariş, " + toplam + " TL"));

var liste = siparisler.stream().map(Siparis::no).toList();  // Java 16

Dikkat

  • stream().toList() ile collect(Collectors.toList()) aynı değildir: birincisi değiştirilemez liste döner, ikincisi değiştirilebilir ArrayList. Geçişte UnsupportedOperationException olarak karşınıza çıkabilir.
  • toList() null elemana izin verir, List.of() vermez.
  • takeWhile / dropWhile sırasız (unordered) akışlarda beklediğiniz sonucu vermez; sıralı kaynaklarda kullanın.

Gerçek projede Maven/Gradle -g eklediği için gerçek ad görünür. Unboxing örneği (2) özellikle önemlidir: Map<String, Integer>'dan gelen null'ın int'e atanması, Java 8'de hiçbir ipucu vermeyen klasik bir üretim hatasıydı.

Java 21 · Virtual Threads (Project Loom)

Milyonlarca eşzamanlı görev, aynı basit kod

Platform thread

~1 MByığın (stack) / thread · OS yönetir · binlerle sınırlı

Havuz dolunca istekler kuyrukta bekler.

Virtual thread

~KBheap'te yaşar · JVM yönetir · milyonlarla ölçeklenir

Reaktif/async karmaşasına gerek kalmadan yüksek throughput.

Ne zaman kazandırır: I/O bekleyen görevlerde — veritabanı, HTTP, kuyruk. CPU yoğun işlerde fark yaratmaz; orada belirleyici olan çekirdek sayısıdır.

Not: Compiler Explorer sandbox'ı yeni thread açmaya izin vermez; bu örnek orada "unable to create native thread" ile durur. Kopyalayıp yerelde java Main.java ile çalıştırın: havuz ≈ 5 sn, sanal thread ≈ 0,1 sn.

Java 8 → Java 21
Virtual thread CPU'yu hızlandırmaz; I/O bekleyen görevlerde ölçeklenebilirliği artırır. Spring Boot 3.2+ tek bir property ile (spring.threads.virtual.enabled=true) açar. Yük testleri farklı davranır: darboğaz thread sayısından veritabanı bağlantı havuzuna kayar. synchronized blokları sanal thread'i sabitler (pinning, Java 24'te düzeldi); ReentrantLock tercih edin, performans ölçümlerini yenileyin. Sunum öncesi bu örneği yerel JDK 21'de bir kez çalıştırıp süreleri not alın; sandbox thread açamadığı için canlı demo yerine "Kopyala" düğmesini kullanın.

Java 21 · JEP 431 — Sequenced Collections

İlk ve son eleman nihayet standart

Java koleksiyonlarında "ilk elemanı al" demenin tek bir yolu yoktu. Her tip için ayrı bir hile gerekiyordu.

Java 8'deki dağınıklık

Tipİlk elemanSon eleman
Listlist.get(0)list.get(list.size() - 1)
Dequedeque.getFirst()deque.getLast()
LinkedHashSetset.iterator().next()Yolu yok, döngü gerek
SortedSetset.first()set.last()

Java 21 ile

var liste = new ArrayList<>(List.of("a", "b", "c"));
liste.getFirst();     // "a"
liste.getLast();      // "c"
liste.reversed();     // [c, b, a] — kopya değil, görünüm

var set = new LinkedHashSet<>(List.of("x", "y"));
set.addFirst("w");    // artık mümkün
set.getLast();        // "y"

var harita = new LinkedHashMap<String, Integer>();
harita.firstEntry();  harita.lastEntry();  harita.reversed();

Arkasında üç yeni arayüz var: SequencedCollection, SequencedSet, SequencedMap. List, Deque, LinkedHashSet, LinkedHashMap ve SortedSet/SortedMap bunları uyguluyor.

Dikkat

  • reversed() bir görünümdür: kaynağı değiştirirseniz görünüm de değişir, kopya maliyeti yoktur.
  • Sırası olmayan koleksiyonlar (HashSet, HashMap) bu arayüzleri uygulamaz; "ilk eleman" onlar için anlamsızdır.
  • Kendi List gerçekleştiriminizi yazdıysanız yeni metotlar varsayılan gövdeyle geldiği için kodunuz kırılmaz.

Java 21 · JEP 439 — Generational ZGC

Büyük heap, küçük duraklama

ZGC, heap boyutundan bağımsız olarak milisaniye altı duraklama hedefleyen çöp toplayıcıdır. Java 21 onu nesil ayrımıyla verimli hale getirdi.

Kısa tarihçe

  • Java 11: ZGC deneysel olarak geldi. Java 15: üretime hazır ilan edildi.
  • Java 21: nesil ayrımı (genç / yaşlı) eklendi. Aynı iş için belirgin biçimde daha az CPU ve bellek.
  • Java 21'de açmak için: -XX:+UseZGC -XX:+ZGenerational

Neden nesil ayrımı önemli

Nesnelerin çoğu kısa yaşar. Nesil ayrımı olmayan toplayıcı her turda tüm heap'i tarar; nesil ayrımı olan, çoğu zaman yalnızca genç bölgeyi tarar. Sonuç: aynı duraklama hedefi için daha az iş, daha az CPU, daha yüksek verim.

Hangi toplayıcıyı seçmeli

ToplayıcıNe zaman
G1 (varsayılan)Çoğu uygulama. Verim ve gecikme arasında dengeli; ayar gerektirmez.
ZGCBüyük heap (onlarca GB ve üzeri) ve gecikmeye duyarlı sistemler: ödeme, borsa, gerçek zamanlı API.
ParallelDuraklama umursanmayan, ham verimin önemli olduğu toplu işler.

Not: Ölçmeden toplayıcı değiştirmeyin. Küçük heap'te ZGC, G1'e göre kazanç sağlamaz.

Java 21 · JEP 452 — Key Encapsulation Mechanism API

Kuantum sonrası kriptografiye hazırlık

İki tarafın ortak bir gizli anahtar üzerinde anlaşmasının standart bir Java arayüzü.

Sorun

Bugün TLS'in temelinde RSA ve eliptik eğri var. Yeterince güçlü bir kuantum bilgisayar bunları kırabilir. Yerlerine gelen kuantum dayanıklı algoritmalar (ML-KEM gibi) klasik "şifrele/çöz" kalıbına değil, anahtar kapsülleme kalıbına dayanıyor: gönderen alıcının açık anahtarıyla rastgele bir gizli anahtar üretip kapsüller, alıcı kendi özel anahtarıyla açar.

Java 21'in getirdiği

KEM kem = KEM.getInstance("DHKEM");

// Gönderen: gizli anahtarı üret ve kapsülle
KEM.Encapsulator e = kem.newEncapsulator(alicininAcikAnahtari);
KEM.Encapsulated k = e.encapsulate();
SecretKey gizli = k.key();          // yerel gizli anahtar
byte[] kapsul  = k.encapsulation(); // karşıya gidecek

// Alıcı: kendi özel anahtarıyla açar
SecretKey ayniGizli = kem.newDecapsulator(ozelAnahtar)
                         .decapsulate(kapsul);

Java 21 arayüzü standartlaştırdı; böylece kütüphaneler ve TLS gerçekleştirimleri algoritmadan bağımsız yazılabiliyor. Kuantum dayanıklı ML-KEM algoritmasının kendisi sonraki sürümlerde JDK'ya eklendi (Java 24, JEP 496).

Ekip için anlamı

  • Uygulama geliştiricisi bu API'yi doğrudan çağırmaz. Onu TLS katmanı ve güvenlik kütüphaneleri kullanır.
  • Önemi şurada: kuantum sonrası geçiş geldiğinde JDK'yı yükseltmek yeterli olacak, uygulama kodunu değiştirmek gerekmeyecek.
  • Uzun ömürlü veri saklıyorsanız ("bugün topla, yarın çöz" saldırısı) bu konuyu takip listenize alın.

Java 21 · JEP 453 — Structured Concurrency (preview)

Alt görevleri tek birim gibi yönetmek

Sanal thread'ler bir görevi ucuz hale getirdi. Structured Concurrency, birden çok görevi birlikte yönetmeyi düzene sokar.

Sorun

Bir isteği karşılamak için iki servise paralel gitmeniz gerekiyor. Biri hata verirse diğerini kim iptal edecek? Ana iş iptal edilirse alt görevler ne olacak? Elle yazılan executor kodunda bu yönetim unutulur ve sızıntı olur: kimsenin beklemediği görevler çalışmaya devam eder.

Yapısal yaklaşım

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {

    Supplier<Musteri> m = scope.fork(() -> musteriGetir(id));
    Supplier<Siparis>  s = scope.fork(() -> siparisGetir(id));

    scope.join();              // ikisini de bekle
    scope.throwIfFailed();     // biri patladıysa fırlat

    return new Sonuc(m.get(), s.get());
}   // blok biterken tüm alt görevler garanti kapanır

Kural şu: alt görevler, kendilerini başlatan bloktan uzun yaşayamaz. Bir dal başarısız olursa ShutdownOnFailure diğerlerini iptal eder; ShutdownOnSuccess ise ilk başarılı sonucu alıp gerisini iptal eder. Thread dökümlerinde ana görev ve alt görevler bir arada görünür.

Durumu

  • Java 19 ve 20'de kuluçka, Java 21'den beri preview. Java 25'te hâlâ preview; API her sürümde biraz değişti.
  • --enable-preview gerektirir, üretimde kullanılmaz.
  • Yine de öğrenmeye değer: sanal thread kullanan ekipler için kalıcı olduğunda varsayılan yazım biçimi bu olacak.

Java 21 · JEP 443 — Unnamed patterns and variables (preview)

Kullanmadığın şeye isim verme

Alt çizgi (_), "burada bir şey var ama benim işim değil" demenin yolu.

Örnekler

// Record ayrıştırmada kullanılmayan bileşen
case Kripto(_, var tutar) -> tutar * 0.01;

// Yakalanan ama okunmayan istisna
try { ... } catch (NumberFormatException _) { return 0; }

// Kullanılmayan döngü değişkeni
for (var _ : siparisler) adet++;

// Kullanılmayan lambda parametresi
harita.forEach((_, deger) -> System.out.println(deger));

// try-with-resources'ta değişkene ihtiyaç yoksa
try (var _ = kilit.al()) { ... }

Neden önemli

  • Niyeti okunur kılar. ignored, unused, e2 gibi uydurma adlar kalkar; okuyan kişi bunun bilinçli olarak kullanılmadığını görür.
  • Derleyici ve statik analiz araçları "kullanılmayan değişken" uyarısı üretmez.
  • Aynı blokta birden çok _ kullanılabilir; isim çakışması olmaz.

Durumu

Java 21'de preview, Java 22'de kalıcı oldu (JEP 456). Java 21 üzerinde denemek için --enable-preview gerekir; Java 22 ve sonrasında bayraksız kullanılır. Not: _ tek başına Java 9'dan beri geçerli bir değişken adı değildi; bu değişiklik o boşluğu anlamlı hale getirdi.

Özetle
